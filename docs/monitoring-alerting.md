# Monitoring: target discovery + alerting

> **What this covers.** The `vms/monitoring/` role ships Prometheus + Grafana
> + four exporters + `node_exporter` on every host and guest. This doc covers
> two layers on top of that:
>
> - **Part 1 — Target discovery and lifecycle.** *Implemented.* How a VM
>   becomes monitored by default, and how monitoring is removed. This is the
>   live mechanism behind "deploy a role, it's scraped" — documented here as
>   it actually works.
> - **Part 2 — Alerting (Alertmanager + ntfy + dead-man's switch).** *Design,
>   not yet built.* The plan that closes out the `prometheus.yml.j2` footer's
>   "Alert rules and Alertmanager wiring land in a follow-up." Treat Part 2 as
>   a working spec: sections that name a file, variable, or KeePassXC entry are
>   what *should* land, with open questions flagged at the end.
>
> When in doubt about Part 1, the repo is authoritative (the task file, the
> Justfile recipe, the consistency check). When in doubt about Part 2, nothing
> is built yet — it's a design.

# Part 1 — Target discovery and lifecycle (implemented)

## The problem this solves

The seed deploy carried a single hand-maintained scrape list
(`monitoring_node_exporter_targets`) plus two more lists that had to stay in
lockstep with it (`monitoring_guest_inventory_groups`, the monitoring role's
`.extra-inventories`, and the explicit `-i` flags of the guest node_exporter
installer). Every VM add/remove meant editing all of them, and forgetting one
produced a silent coverage gap.

## How it works

The source of truth is a committed per-role marker file,
`vms/<role>/monitoring-target.yml`. Its **presence** means "scrape this VM";
its **absence** means "don't." Everything else is derived from it:

```
vms/<role>/monitoring-target.yml   (committed; host + instance == role name)
        │
        ├─ discover_targets.yml finds every vms/*/monitoring-target.yml and builds
        │     • monitoring_node_exporter_targets   (the scrape list)
        │     • monitoring_guest_inventory_groups  (drives /etc/hosts via hosts_file.yml)
        │
        ├─ .extra-inventories globs vms/*/ansible/inventory.yml so the real (gitignored)
        │     IP of each monitored guest is loaded for /etc/hosts resolution
        │
        └─ `just monitoring-guests` installs node_exporter into exactly the opted-in roles
```

Why a committed file rather than Ansible group membership: inventories are
gitignored and regenerated by `scripts/write-inventory.sh`, so a group edited
into one is neither visible in `git status` nor durable across `just
inventory`. A committed marker is both.

- **Default-on.** The marker ships in `vms/_template/`, so a role cloned from
  the template inherits it; the `__ROLE__` sed-rename fills in its `host` /
  `instance`. No edit to the monitoring role is needed to monitor a new VM.
- **Opt-out is git-visible.** `git rm vms/<role>/monitoring-target.yml` shows
  in `git status` and self-cleans when the role directory is removed. `rootca`
  keeps no marker — the documented air-gap exclusion.
- **Per-VM customization later** is a YAML field addition to the marker (see
  [Per-VM customization](#per-vm-customization-future)), not a refactor.

## The files

These are live in the repo — the snippet below is the heart of it; the rest
are pointers so this doc doesn't drift from the code.

**`vms/monitoring/ansible/roles/monitoring/tasks/discover_targets.yml`** — runs
first in `tasks/main.yml`, before `hosts_file.yml`/`config.yml` consume its
facts. `find` is delegated to `localhost` (the control node, where the repo is
checked out); `lookup('file', ...)` also runs on the control node, so both
resolve against the repo tree regardless of which host the play targets. The
`fileglob` lookup can't do directory wildcards (`vms/*/...`), which is why
`find` with `recurse` is the working idiom.

```yaml
- name: Find per-role monitoring-target.yml files
  ansible.builtin.find:
    paths: "{{ playbook_dir }}/../.."   # vms/ — playbook_dir is vms/monitoring/ansible
    patterns: monitoring-target.yml
    recurse: true
    file_type: file
  register: monitoring_target_find
  delegate_to: localhost
  become: false

- name: Reduce to role marker paths (drop vms/_template and other scaffolding)
  ansible.builtin.set_fact:
    monitoring_target_files: >-
      {{ monitoring_target_find.files | map(attribute='path')
         | reject('search', '/_') | sort }}

- name: Load discovered targets into a list of {host, instance} dicts
  ansible.builtin.set_fact:
    monitoring_discovered_targets: >-
      {{ monitoring_discovered_targets | default([])
         + [ lookup('file', item) | from_yaml ] }}
  loop: "{{ monitoring_target_files }}"
  loop_control:
    label: "{{ item | basename }}"

- name: Compose the scrape list and the /etc/hosts group list
  ansible.builtin.set_fact:
    monitoring_node_exporter_targets: >-
      {{ monitoring_static_targets
         + (monitoring_discovered_targets | default([]) | sort(attribute='instance')) }}
    monitoring_guest_inventory_groups: >-
      {{ monitoring_discovered_targets | default([])
         | map(attribute='instance')
         | map('regex_replace', '-', '_')
         | map('regex_replace', '$', '_servers') | list }}
```

For the current lab this yields `monitoring_static_targets` (monitoring,
pve12t, pve13m, pve13t, pbs01) plus the five discovered guests (amp-game, llm,
nemoclaw, openbao, openclaw), and `monitoring_guest_inventory_groups` =
`[amp_game_servers, llm_servers, nemoclaw_servers, openbao_servers,
openclaw_servers]` — the same coverage as the pre-discovery hand-maintained
list, now derived.

The supporting pieces:

- **`defaults/main.yml`** — holds `monitoring_static_targets` (the non-role
  hosts, explicit because they aren't managed under `vms/<role>/`).
  `monitoring_node_exporter_targets` and `monitoring_guest_inventory_groups`
  are seeded `[]` and filled by discovery.
- **`vms/_template/monitoring-target.yml`** — the default-on marker, `host` /
  `instance` set to `__ROLE__`.
- **`vms/<role>/monitoring-target.yml`** — one per monitored role
  (openbao, llm, amp-game, openclaw, nemoclaw today). `host`/`instance` ==
  the role name.
- **`vms/monitoring/ansible/.extra-inventories`** — a glob
  (`vms/*/ansible/inventory.yml`) so every monitored guest's gitignored IP is
  loaded for `/etc/hosts`. The `Justfile` `ansible`/`ansible-check` loaders
  glob-expand each line. Loading an unmonitored role's inventory is harmless —
  it just never appears in the scrape list.
- **`Justfile` → `just monitoring-guests`** — globs `vms/*/monitoring-target.yml`,
  maps each to its `ansible/inventory.yml`, and runs
  `install-node-exporter-guests.yml` against exactly those. Skips
  `vms/_template` and roles with no hydrated inventory (with a hint).
- **`scripts/check-role-consistency.sh` (check 7)** — when a marker is present,
  asserts it declares `host:` + `instance:`, carries no unsubstituted
  `__ROLE__`, and uses an `instance` label unique across roles (Prometheus
  de-dupes by `(job, instance)`, so a collision silently drops a VM's metrics).
  Run via `just check-roles`.

## Lifecycle

Adding/removing a VM is a **scrape-target change, not a config-list edit** —
and (once Part 2 lands) an alert-coverage change with no rule edits, because
the planned rules match on labels (`job="node_exporter"`), not VM names.

### Adding a new VM (default — auto-monitored)

1. Deploy the role per [`docs/deploying-vms.md`](deploying-vms.md). The
   `vms/_template/` clone already carries `monitoring-target.yml`; the
   `__ROLE__` sed-rename fills it in.
2. Verify: `cat vms/<new-role>/monitoring-target.yml`.
3. Install node_exporter inside the guest: `just monitoring-guests`
   (idempotent; no-op for roles already covered).
4. Re-render Prometheus's scrape config + `/etc/hosts`:
   `just ansible monitoring`.
5. Confirm the target is `UP` at
   `http://<monitoring-vm-ip>:9090/classic/targets`.

The VM is now scraped and shows on the **Lab Rightsizing** and **Node Exporter
Full** dashboards. PVE-side coverage (via `pve-exporter`) was there from the
moment it appeared in the PVE inventory — that doesn't depend on the marker.

### Removing a VM

Delete the marker **before** destroying the VM, so Prometheus stops scraping a
target cleanly rather than (once Part 2's `NodeDown` exists) paging on a target
that vanished from under it:

```bash
git rm vms/<role>/monitoring-target.yml   # or rm, if not yet committed
just ansible monitoring                   # stops scraping; hosts_file.yml re-templates /etc/hosts
just destroy <role>                       # then tear down the VM
```

`git rm -rf vms/<role>` if the role is gone for good — the marker goes with it.

### Opting a VM out (it should exist, but not be scraped)

The canonical case is `rootca` — air-gapped, USB-HSM-pinned, security posture
rules out an open exporter port.

1. Keep (or `git rm`) no `monitoring-target.yml` for that role.
2. Document *why* in the role's README, so the exclusion is discoverable
   without grepping the monitoring docs.
3. `just ansible monitoring` to drop any stale scrape entry.

`rootca` already keeps no marker and its README explains the exclusion.

### Failure modes worth knowing

| Failure | What happens | Mitigation |
| --- | --- | --- |
| Clone template, forget to substitute `__ROLE__` | Discovery loads a target with literal `__ROLE__` host; the scrape fails to resolve. | `check-role-consistency.sh` check 7 fails on `unsubstituted-__ROLE__`; the `sed`-rename pass per `vms/_template/README.md` runs against every file. |
| Add marker but skip `just monitoring-guests` | Prometheus shows the new target DOWN until node_exporter is installed. | Run `just monitoring-guests` right after deploying a role (before `just ansible monitoring`). Once Part 2 lands, `NodeDown` is also the safety net. |
| Delete marker, forget `just ansible monitoring` | Prometheus keeps a stale scrape entry (no spurious alert — the VM may still be up). | Re-run `just ansible monitoring`. A pre-commit reminder on `vms/*/monitoring-target.yml` is possible but low-value. |
| Two roles with the same `instance` label | Prometheus de-dupes by `(job, instance)`; the second silently overwrites the first. | `check-role-consistency.sh` check 7 enforces uniqueness across roles. |

### Per-VM customization (future)

The marker is the right place to land per-VM overrides if they're ever needed —
e.g. a looser CPU-pressure threshold for `amp-game`, which bursts hard at game
session start:

```yaml
host: amp-game
instance: amp-game
alerts:
  cpu_pressure_threshold: 0.20
```

`discover_targets.yml` would surface these into Jinja and Part 2's
`prometheus-alerts.yml.j2` would template per-VM rules inheriting the global
threshold unless overridden. Deferred until the alert noise floor is calibrated
and a real override is demanded.

# Part 2 — Alerting: Alertmanager + ntfy + dead-man's switch (deferred design)

> **Not built.** Nothing below exists in the repo yet. This is the design for
> the alerting follow-up. Until it lands, alerts neither evaluate nor notify —
> the discovery mechanism in Part 1 only governs what is *scraped*.

## Goals

Two user-facing alert classes, plus the infrastructure to keep the signal
honest:

- **VM down** — a VM (or a cluster host, or `pbs01`) stops responding.
- **Disk space low** — a filesystem inside a guest, on a PVE host, or a
  Proxmox storage pool crosses a threshold.
- **Backup failure** — PBS verify failed, or a snapshot is stale.
- **UPS on battery** — sustained, not transient line dips.
- **Dead-man's switch** — whole-cluster failure.

Eight starter rules; calibration and noise control are out of scope for the
MVP.

## Decisions

### 1. Routing — Alertmanager, not Grafana unified alerting

Grafana's built-in alerting avoids a second daemon, but its rules would live in
Grafana's SQLite (or YAML provisioned through Grafana's API) — a second source
of truth alongside the role's existing `prometheus-rules.yml.j2`. The role's
discipline elsewhere is Jinja → Ansible → repo; Alertmanager keeps one template
pattern, one config language, both versioned. Single instance on the monitoring
VM, no clustering — matching Prometheus and Grafana on the same host.

### 2. Notification channel — ntfy

ntfy wins on zero accounts, no SMTP plumbing, and mobile push via the app
subscribing to a topic. The topic name acts as the access key — generated
random, stashed in KeePassXC, never committed. Email can be added later via
ntfy's own SMTP relay; that's additive, not a swap.

> **Open decision — phone reachability (self-hosted vs ntfy.sh).** Self-hosting
> ntfy on a LAN-only VM only pushes to your phone when the phone is on the LAN.
> For alerts *away from home*, either expose ntfy to the internet (reverse
> proxy + auth) or use the public `ntfy.sh` server (zero infra; the random
> topic name is the only secret). Settle this before building — it changes the
> ntfy task, the firewall rules, and the `monitoring_ntfy_base_url` default.
> See [Open questions](#open-questions-part-2).

### 3. Cluster-down blind spot — healthchecks.io dead-man's switch

Alertmanager runs on the cluster it's watching, so a whole-cluster failure is
also an alerting failure. The canonical answer is a **watchdog alert** that
always fires, routed to a receiver that pings an external health-check every
minute; if the pings stop, the external service notifies the operator.
healthchecks.io's free tier covers this (one HTTPS endpoint, email on missed
pings). Self-hosting healthchecks is deferred — the whole value of this leg is
that it sits *outside* the cluster's failure domain.

## Scope

In scope: single-instance Alertmanager; ntfy (single topic, mobile-app
subscription); an `alertmanager.yml` template with `ntfy` + `watchdog`
receivers and routes; a `prometheus-alerts.yml` template with the eight rules
below; the `Watchdog` rule routed to healthchecks.io; operator ceremony for the
two new KeePassXC entries; README ports/credentials/backlinks updates.

Out of scope: inhibition/silence beyond defaults; HA Alertmanager; email-relay
receiver; `snmp_exporter` for the switch (separate Phase 2); Loki / log alerts.

## Architecture

```
                       Prometheus (monitoring VM)
                              │ evaluates rules every 15s
                              ▼
                       Pending → Firing
                              │ POST /api/v2/alerts
                              ▼
                    Alertmanager (monitoring VM)
                  ┌───────────┴───────────────────┐
        normal severity routes              watchdog route
                  ▼                               ▼
              ntfy (self-hosted)           healthchecks.io (Internet)
                  ▼                               ▼
         operator phone push           if pings stop → email operator
```

Every box runs on the monitoring VM except healthchecks.io. The watchdog
receiver's Internet egress is the single out-of-cluster signal path.

## Alert rules

Eight rules, all from metrics already collected, grouped in
`prometheus-alerts.yml.j2` under three rule groups so dashboards/ACLs can filter
by group.

| Alert | Group | Severity | `for` | Expression |
| --- | --- | --- | --- | --- |
| `NodeDown` | infrastructure | critical | 5m | `up{job="node_exporter"} == 0` |
| `PVENodeDown` | infrastructure | critical | 5m | `pve_up{id=~"node/.*"} == 0` |
| `DiskSpaceLow` | infrastructure | warning | 30m | `(node_filesystem_avail_bytes{mountpoint="/",fstype!~"tmpfs\|overlay"} / node_filesystem_size_bytes) < 0.15` |
| `DiskSpaceCritical` | infrastructure | critical | 5m | `(node_filesystem_avail_bytes{mountpoint="/",fstype!~"tmpfs\|overlay"} / node_filesystem_size_bytes) < 0.05` |
| `PVEStorageFilling` | infrastructure | warning | 1h | `pve_disk_usage_bytes{id=~"storage/.*"} / pve_disk_size_bytes{id=~"storage/.*"} > 0.85` |
| `PBSBackupStale` | backups | warning | 10m | confirm — see below |
| `PBSVerifyFailed` | backups | critical | 10m | confirm — see below |
| `UPSOnBattery` | power | critical | 60s | `nut_status_flags{flag="OB"} == 1` |
| `Watchdog` | infrastructure | none | 0s | `vector(1)` |

`Watchdog` always fires (`vector(1)`); severity `none`, routed exclusively to
the watchdog receiver, never to ntfy.

### Metric names to confirm on the live exporters

Two PBS-exporter metric names must be confirmed against the deployed version
before the rule text is committed — natrontech has renamed fields across minor
releases:

```bash
curl -sf http://127.0.0.1:10019/metrics | grep -E '^pbs_' | awk '{print $1}' | sort -u
```

Look for the **last successful backup time** (typically `pbs_snapshot_*` with a
`time`/`timestamp` field) and the **verify state** (typically
`pbs_snapshot_verify_state`). Pin the rules to the same
`monitoring_pbs_exporter_version` the role pins.

`pve_up` carries an `id` label distinguishing nodes (`node/<name>`) from guests
(`qemu/<vmid>`). A future `GuestVMDown` rule on `pve_up{id=~"qemu/.*"}` would
catch a VM dying when its in-guest node_exporter still briefly looks alive —
`NodeDown` catches the exporter side, that rule the cluster side. See
[Open questions](#open-questions-part-2).

### Severity → routing

- `critical` → ntfy, high priority + tags, repeat every 1h.
- `warning` → ntfy, default priority, repeat every 4h.
- `Watchdog`'s `none` → matched by a separate route to the `watchdog` receiver.

## File-by-file plan (alerting)

All new unless noted. The role's tasks live in
`vms/monitoring/ansible/roles/monitoring/`.

**`defaults/main.yml`** — append an Alertmanager + thresholds + ntfy +
healthchecks block:

```yaml
# --- Alertmanager ---
monitoring_alertmanager_port: 9093
monitoring_alertmanager_config: /etc/prometheus/alertmanager.yml
monitoring_alertmanager_storage: /var/lib/alertmanager
# Install method — see Open questions. Default apt (prometheus-alertmanager).

# --- Alert thresholds (calibration is a defaults-only edit) ---
monitoring_disk_low_warn_ratio: 0.15
monitoring_disk_low_crit_ratio: 0.05
monitoring_pve_storage_fill_warn_ratio: 0.85
monitoring_pbs_backup_stale_seconds: 129600   # 36h
monitoring_alert_repeat_warning: 4h
monitoring_alert_repeat_critical: 1h

# --- ntfy (self-hosted; topic is the access key, lives in KeePassXC) ---
monitoring_ntfy_listen_http: ":8080"
monitoring_ntfy_base_url: "http://monitoring:8080"   # revisit per phone-reachability decision
monitoring_ntfy_cache_file: /var/cache/ntfy/cache.db
monitoring_ntfy_topic_placeholder: "REPLACE_WITH_KEEPASSXC_NTFY_TOPIC"

# --- healthchecks.io dead-man's-switch (full ping URL is a secret) ---
monitoring_healthchecks_url_placeholder: "REPLACE_WITH_KEEPASSXC_HEALTHCHECKS_URL"
```

**`tasks/alertmanager.yml`** — install Alertmanager (apt or tarball, see Open
questions), lay down the config template with the healthchecks placeholder,
register a systemd unit, open port 9093 via `firewall.yml`. The
healthchecks-URL-carrying file uses `force: false` so re-runs don't clobber the
operator's pasted value — same shape as `/etc/prometheus/pve.yml` and
`pbs-exporter.env`.

**`tasks/ntfy.yml`** — install ntfy (apt from heckel.io's repo by default; see
Open questions for Docker), lay down `/etc/ntfy/server.yml` from
`ntfy.server.yml.j2`.

**`tasks/alert_rules.yml`** — render `prometheus-alerts.yml.j2` to
`/etc/prometheus/rules/alerts.yml`, `validate: "promtool check rules %s"`
(mirrors the existing recording-rules task in `config.yml`).

**`tasks/main.yml`** — add the three alerting imports after the exporter tasks
and before `config.yml` (the discovery import is already first, from Part 1):

```yaml
- name: Install Alertmanager
  ansible.builtin.import_tasks: alertmanager.yml
- name: Install ntfy server
  ansible.builtin.import_tasks: ntfy.yml
- name: Render Prometheus alert rules
  ansible.builtin.import_tasks: alert_rules.yml
```

**`templates/prometheus.yml.j2`** — replace the footer comment with the real
wiring:

```yaml
alerting:
  alertmanagers:
    - static_configs:
        - targets: ['127.0.0.1:{{ monitoring_alertmanager_port }}']

rule_files:
  - /etc/prometheus/rules/homelab.yml   # recording rules (existing)
  - /etc/prometheus/rules/alerts.yml    # alert rules (new)
```

**`templates/alertmanager.yml.j2`** — one config, both routes:

```yaml
global:
  resolve_timeout: 5m

route:
  receiver: ntfy-default
  group_by: ['alertname', 'severity']
  group_wait: 30s
  group_interval: 5m
  routes:
    - matchers: [ 'alertname = "Watchdog"' ]
      receiver: watchdog
      group_wait: 0s
      group_interval: 60s
      repeat_interval: 60s
    - matchers: [ 'severity = "critical"' ]
      receiver: ntfy-critical
      repeat_interval: {{ monitoring_alert_repeat_critical }}
    - matchers: [ 'severity = "warning"' ]
      receiver: ntfy-warning
      repeat_interval: {{ monitoring_alert_repeat_warning }}

receivers:
  - name: ntfy-default
    webhook_configs:
      - url: "{{ monitoring_ntfy_base_url }}/{{ monitoring_ntfy_topic_placeholder }}"
        send_resolved: true
  - name: ntfy-warning
    webhook_configs:
      - url: "{{ monitoring_ntfy_base_url }}/{{ monitoring_ntfy_topic_placeholder }}?priority=default&tags=warning"
        send_resolved: true
  - name: ntfy-critical
    webhook_configs:
      - url: "{{ monitoring_ntfy_base_url }}/{{ monitoring_ntfy_topic_placeholder }}?priority=high&tags=rotating_light"
        send_resolved: true
  # Dead-man's switch. Operator pastes the healthchecks URL post-Ansible (force: false).
  - name: watchdog
    webhook_configs:
      - url: "{{ monitoring_healthchecks_url_placeholder }}"
        send_resolved: false
```

Confirm ntfy's `?priority=…&tags=…` webhook query syntax against current ntfy
docs at implementation time.

**`templates/prometheus-alerts.yml.j2`** — the eight rules across the three
groups. The Jinja-vs-Go-template escaping matters: annotations reference
Prometheus's `{{ $labels.foo }}`, so write them as `{{ '{{' }} $labels.foo {{ '}}' }}`
or Ansible swallows them at template time. Representative rule:

```yaml
groups:
  - name: infrastructure
    interval: 30s
    rules:
      - alert: NodeDown
        expr: up{job="node_exporter"} == 0
        for: 5m
        labels: { severity: critical }
        annotations:
          summary: "{{ '{{' }} $labels.instance {{ '}}' }} node_exporter unreachable"
          description: "Prometheus could not scrape {{ '{{' }} $labels.instance {{ '}}' }}:9100 for 5m — host down, exporter crashed, or network path broken."
      # DiskSpaceLow/Critical, PVENodeDown, PVEStorageFilling, Watchdog ...
  - name: backups
    interval: 60s
    rules:
      - alert: PBSBackupStale     # expr uses the confirmed metric name (see above)
        expr: (time() - pbs_snapshot_last_backup_timestamp) > {{ monitoring_pbs_backup_stale_seconds }}
        for: 10m
        labels: { severity: warning }
      - alert: PBSVerifyFailed
        expr: pbs_snapshot_verify_state == 0
        for: 10m
        labels: { severity: critical }
  - name: power
    interval: 30s
    rules:
      - alert: UPSOnBattery
        expr: nut_status_flags{flag="OB"} == 1
        for: 60s
        labels: { severity: critical }
```

**`templates/ntfy.server.yml.j2`** — minimal config; `auth-default-access:
deny-all` so the topic name is the only publish credential (acceptable while
LAN-only; revisit under the phone-reachability decision):

base-url: "{{ monitoring_ntfy_base_url }}"

## Operator ceremony — configure alerting + your phone

Two one-time human steps that never touch committed code, then the paste.

1. **ntfy / your phone.** Install the ntfy app, subscribe to the topic from
   KeePassXC (`Homelab/Alerting/ntfy-topic`). (If the phone-reachability
   decision lands on `ntfy.sh`, point the app at `ntfy.sh`; if self-hosted +
   LAN-only, the phone receives alerts only on the LAN.)
2. **healthchecks.io.** Create an account + one check, set its email
   notification to your address, copy the ping URL into KeePassXC
   (`Homelab/Alerting/healthchecks-url`).
3. **Paste the secrets on the VM:**

```bash
ssh monitoring-admin@<vm-ip>
sudoedit /etc/prometheus/alertmanager.yml   # replace REPLACE_WITH_KEEPASSXC_NTFY_TOPIC (3 URLs)
                                            # replace REPLACE_WITH_KEEPASSXC_HEALTHCHECKS_URL (watchdog)
sudo systemctl reload prometheus-alertmanager
```

The placeholders are obvious sentinels — they can't function as a real value,
so a forgotten paste fails loudly at the first POST rather than silently
misrouting. `force: false` means `just ansible monitoring` won't clobber the
pasted values.

## Verification

After the ceremony, in order:

1. **Alertmanager up + Prometheus knows it:**
   `curl -sf http://<vm-ip>:9090/api/v1/alertmanagers | jq .` and
   `curl -sf http://<vm-ip>:9093/api/v2/status | jq .`
2. **Rules loaded:**
   `curl -sf http://<vm-ip>:9090/api/v1/rules | jq '.data.groups[].rules[] | {name, state}'`
   — `Watchdog` should be `firing`, the rest `inactive`.
3. **ntfy end-to-end:**
   `amtool --alertmanager.url=http://127.0.0.1:9093 alert add TestAlert severity=warning --annotation=summary="sanity check"`
   — phone should buzz. If not: `journalctl -u prometheus-alertmanager -n 50`
   (webhook POST + 2xx?), `journalctl -u ntfy -n 50`; a 403 means the topic in
   the config ≠ the topic the app subscribes to.
4. **Dead-man's switch:** the healthchecks.io check goes green within ~90s; stop
   Alertmanager to confirm it emails after 2× the timeout, then restart.
5. **Real signals:** fill a guest's root fs past the warn ratio (`fallocate`,
   then `rm`) for `DiskSpaceLow`; pull AC for >60s for `UPSOnBattery`. For the
   PBS rules, set `monitoring_pbs_backup_stale_seconds: 60` in a scratch
   override rather than touching the real backup chain.

## Open questions (Part 2)

1. **Alertmanager install — apt vs tarball.** apt (`prometheus-alertmanager`)
   mirrors how Prometheus is installed; tarball pins the version like the
   pve/pbs exporters. Default apt unless a needed routing primitive is
   newer-only.
2. **ntfy install — apt vs Docker.** apt (heckel.io) gives a native systemd
   unit and easy journalctl; Docker reuses the existing `docker.io` from the
   nut-exporter but adds log-inspection indirection and ufw/iptables shimming.
   Default apt.
3. **Phone reachability — self-hosted LAN-only vs reachable vs ntfy.sh.** The
   one that actually shapes the build (see Decision §2). Decide before writing
   the ntfy task.
4. **`GuestVMDown` rule.** Add `pve_up{id=~"qemu/.*"} == 0` either default-all
   or scoped to a curated critical set. Defer until the MVP has run a week and
   real shutdown patterns are visible.
